# Virus Check Desktop

Local-first malware triage for Windows. Static analysis of any file at any size, plus isolated detonation in Windows Sandbox.
Branch: `main` (feature work in `feat/*`). Delivery: `single-pr` forecast pending. Runner: `cargo test --workspace`.

## Specs

S1. "no tenga límite de tamaño de archivo"
   - No artificial cap of our own: hashing, type identification and streaming inspection work on any size the filesystem can store.
   - Each engine declares what it actually inspected: `Coverage::Complete | Partial { scanned_bytes, reason } | None { reason }`. No single "clean" verdict hides an engine that skipped bytes.
   - Acceptance: scanning a file larger than an engine's own cap still produces a full report with that engine marked `Partial`/`None` and the cap named in `reason`.
   - Check: unit test with a stub engine that reports `Partial`; integration scan of a sparse multi-GiB file must not load it into memory.

S2. "que ejecute todos los tipos de archivo"
   - Accepted interpretation (assumption, not literal): every file type is *analyzed*; only types Windows can execute are *detonated*, and always inside an isolated sandbox.
   - Static coverage is universal: content-type by magic bytes, not extension.
   - Detonation applies to PE, scripts, and Office documents with macros, in Windows Sandbox with a read-only mapped drop folder.
   - Acceptance: a file with an unknown or disguised extension is still typed and analyzed; a request to detonate an unsupported type returns a typed `Skipped` reason instead of failing.

S3. "se ejecute en local con un programa"
   - Offline by default. No file leaves the machine. Optional network lookups are off unless the user enables them.
   - Acceptance: the scanner runs with no network access and produces a complete report.

S4. "Se subiría a GitHub con el nombre de Virus Check Desktop"
   - Repository slug `virus-check-desktop`, product name "Virus Check Desktop".
   - Acceptance: repo builds from a clean clone with documented prerequisites only.

S5. Honest verdicts
   - `Malicious | Suspicious | Undetected | Inconclusive | Unknown`. `Undetected` means "no engine in this run reported a detection", never "safe". `Inconclusive` when some inspected range was skipped; `Unknown` when nothing was inspected.
   - Acceptance: aggregation table covered by tests.

## Tasks

- T1 core: streaming digests, content typing, report/verdict model, scanner, CLI. S1, S2, S5. inline. done → b1fa47f
- T1b hashing throughput: three threads over one sequential read above 4 MiB. S1. inline. done → ef0e891
- T2a PE header structure: section table, entry point bounds, W+X sections, CLR flag. S2. inline. done → b1fa47f
- T2b PE body facts: per-section entropy, import table, packer hints (bounded reads), structured facts. S2. inline. done → 44a8798
- T2c container recursion: ZIP/7z/gzip extraction with depth and byte limits, re-entering the pipeline. S1, S2. inline.
- T3 ClamAV engine: local `clamscan`, `FOUND` parsing, 2 GiB cap reported as Partial{0}, timeout and process boundary. S1, S5. inline. done → 165fb40
- T3b ClamAV daemon: managed `clamd` on loopback port 3311, config under `%LOCALAPPDATA%`, reused if already listening, stopped when this run owns it, fallback to `clamscan` with the reason in a fact. S1. inline. done. 8 files in 8.3 s versus ~53 s with one process per file.
- T4 Defender engine: `MpCmdRun -Scan -ScanType 3 -File` with `-DisableRemediation`, exit-code contract, threat-name parsing. S5. inline. done. Verified against EICAR inside a zip (0.16 s) and end to end through the CLI.
- T5 YARA engine: in-process `yara-x` (no spawn), embedded rules plus `%LOCALAPPDATA%\VirusCheckDesktop\rules`, severity from rule metadata. S1, S2. inline. done. Verified live with a builtin rule and a user rule.
- T6 sandbox: `.wsb` generation, read-only payload, guest PowerShell telemetry (processes, TCP, DNS, file drops, registry), dropped files copied back, hard timeout and teardown. S2. inline. done. Verified against a test script and against the timeout path.
- T7 UI: egui/eframe desktop shell over the core, background worker thread, progress and cancel, per-file detail with hashes, facts and findings, Copy JSON, drag and drop. S3, S4. inline. done. Verified by screenshot of a real 3-file scan.
- T8 packaging + CI: `cargo build --release` artifacts, GitHub Actions on windows-latest (fmt, clippy `-D warnings`, tests, build), tag-driven release with both executables. S4. inline. done.
- T9 docs: README (install, architecture, limits, measurements), SECURITY.md with the threat model and the backend boundaries. S1, S4. inline. done.
- T10 directory scanning: recursive walk without following links, per-file reports, errors listed separately, JSON tree report. S1. inline. done.

L19. (Superseded by L20.) T4 was first abandoned on the belief that `MpCmdRun`'s custom scan is a no-op.

L20. T4 reversed with a decisive experiment. Timing was never evidence of a no-op: Defender keeps a scan cache that real-time protection populates when a file is written, which is why 100 MB of random bytes "scanned" in 30 ms and a 2000-file tree in 140 ms — both had just been read by RTP. The test that discriminates: EICAR built inside a zip **in memory** (the plaintext never touches the disk, so RTP cannot pre-scan the content) and scanned with `-DisableRemediation`. `MpCmdRun` returned exit 2 in 0.16 s with `Threat : Virus:DOS/EICAR_Test_File` and `file: eicar.zip->eicar.txt`, proving it reads content, extracts archives, and reports the signature. The engine now ships with `-DisableRemediation` (a scanner must never delete the user's files), the exit code as the contract, the `Threat` line parsed for the name, and a `caveat` fact stating that a clean answer may come from the cache and that excluded paths are invisible without admin rights. End-to-end through our CLI on that zip: `defender` malicious in 67 ms, `clamav` EICAR in 6.3 s, verdict `MALICIOUS`, exit 1.

L24. T6 sandbox shipped after a chain of real obstacles, each solved with evidence. L31. Security review of the whole repository with four read-only lenses (risk, readability, reliability, plus a refuter pass over the consolidated findings), then the fixes that survived. Two of the findings were reproducible false-clean paths, which is the one failure class this project treats as unacceptable:

1. **clamscan defaults skip large files and exit 0.** A 291.6 MiB file produced `coverage: complete` / `UNDETECTED` / exit 0 while libclamav logged `File too large (305750088 bytes), ignoring` under `--debug`. First fix attempt passed `--max-filesize=2048 --max-scansize=2048`; measuring against `clamscan --debug` showed the file was still skipped, because a bare number there is **bytes**, not megabytes. `--max-filesize=2048M --max-scansize=2048M --max-scantime=600000` removes the marker (verified with the exact argument vector the engine now passes), and the strings are pinned by a test so the suffix cannot be dropped again. A 2.5 GiB sparse file still hits our own guard and now reports `0 B scanned` + `INCONCLUSIVE`. Output the host cannot read is now a failed engine, not an empty clean scan.
2. **Exit 0 meant "nothing found" even when nothing was proved.** Single files now exit 2 for Inconclusive/Unknown; trees exit 2 when any file was inconclusive, unknown or unreadable. README documents it.
3. **The portable MSI was executed unverified.** The MSI is not Authenticode-signed, so the exact file is pinned by SHA-256 (`58876d43…`, taken from the release metadata and confirmed against a fresh 224,510,215-byte download). A mismatch deletes the file before `msiexec` and says so. The download goes to a per-run temp directory, uses absolute `%SystemRoot%\System32` binaries, and the PowerShell fallback reads URL and destination from environment variables instead of interpolating them into `-Command` (a profile path with an apostrophe used to break or extend the script).
4. **An interrupted install reported "ready".** Installation now requires `main` **and** `daily` under `database/`; a tree with libraries but no signatures resumes at the update step, and the setup dialog reopens instead of closing.
5. **Any listener on 127.0.0.1:3311 was adopted as the scanner.** Adoption now requires the PID in `clamd.pid` to be a live `clamd.exe`; otherwise the engine refuses that port and falls back to `clamscan` with the reason recorded. `owner.pid` is kept when the daemon refuses to stop.
6. **Administrator elevation read a fixed-name script from `%TEMP%`.** `Start-Process -Verb RunAs` now receives `-EncodedCommand` (base64 UTF-16LE) instead of `-File`, so there is no writable file between write and elevated read. No dependency added: the encoder is 20 lines with tests.
7. **The Sandbox VM leaked on every path except the host timeout.** A `SessionGuard` now kills the session and `WindowsSandboxServer` when the function returns, including the "session never appeared" error. The guest-written `result.json` is capped at 8 MiB and 10,000 entries per list, and Sandboxie's missing report is an error instead of an empty success. `sandboxie_watch.ps1` quotes the sample path (`-ArgumentList` joins without quoting, so "John Smith" broke the launch) and only sets `executed` after the sample's process is actually observed.
8. **UI Cancel could never fire.** The flag was written by the worker thread that was blocked inside the scan; it is now stored from the UI thread. `libclamav` also gets a 600 s `MaxScanTime` instead of 0.
9. **`SetDllDirectoryW` left a user-writable directory in the process search path.** The previous value is saved with `GetDllDirectoryW` and restored as soon as `LoadLibrary` returns.
10. **Smaller correctness fixes:** `clamscan` gets an absolute target path so a file named `--help` cannot be parsed as an option; `vcd clamav status` and the setup dialog share one discovery answer (PATH included) and now report the system install even when the portable tree has the newer database; the CI release job reads the tag from `env:` instead of interpolating `github.ref_name` into PowerShell with `contents: write`; the CLI validates `--timeout > --duration`, names each range, drops the undocumented `sandbox` backend alias, and prints the backend once; docs no longer claim ClamAV is never linked or that the daemon stays warm.

The lie was in the message, which now says the sandbox launches the file as-is and therefore needs an executable name. Renaming a sample before executing it changes what the sample sees, so it is a product decision, not a bug fix.
